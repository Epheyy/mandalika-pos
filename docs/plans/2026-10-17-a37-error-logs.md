## Decisions (planner recommendations)

1. One redactor per language, one shared vector file. TS packages/sync/src/redact.ts (exported from index.ts;
   POS already depends on @mandalika/sync, no new edge). Go backend/internal/redact. Shared fixture
   packages/sync/src/__fixtures__/redact-vectors.json run by vitest AND go test (parity guard, like promoValidate).
2. Two tiers (pending owner Q1): SECRETS = keys pin, pinHash, password, token, accessToken, refreshToken,
   authorization, cookie, secret, apiKey + Bearer/JWT string patterns; LOGS = SECRETS + PII keys (phone, email,
   customerPhone, customerEmail, address, nik) + string patterns (email; Indonesian phone +62/62/0 then 8 then 7-12
   digits with token boundaries; URL query params token, access_token, key, sig, password). Error logs and
   diagnostics use LOGS; toReviewReport uses SECRETS (head office needs the customer to resolve the item).
3. Redactor contract: pure; deep-clones (never mutates outbox items, the retry source of truth); recursive through
   objects/arrays; cycle-safe (WeakSet, emits [Circular]); depth cap 8; string cap 2 KB; total output cap 32 KB
   (emits _truncated + bytes); Error becomes name/message/stack/cause following the cause chain (depth-capped);
   case-insensitive key match; replacement [REDACTED]. Keys exempt from the phone pattern: id, *Id, idempotencyKey,
   orderNumber, transferNo, sku, barcode. Applied to message, action, breadcrumb labels and payload.
4. Server never trusts the client: redaction lives in write.Repo.InsertErrorLogs (covers HTTP + panic paths), plus
   handler hardening: MaxBytesReader 256 KB, max 50 items, decode error = 400, per-row sanitize (NUL strip and
   re-encode via the generalized sanitizeReviewPayload helpers), one tx or multi-row insert (no partial batch).
   Also replace the top-level pin delete in sanitizeReviewPayload with redact.Secrets (recursive backstop).
   The redactor call in the panic path must itself be recover-wrapped (fall back to dropping the payload).
5. Retention = in-process, no new infra. write.Repo.SweepErrorLogs(ctx, batch 1000, maxBatches 20): each batch is a
   short tx taking pg_try_advisory_xact_lock (skip if another instance holds it), then
   DELETE FROM error_logs WHERE id IN (SELECT id FROM error_logs WHERE created_at < now() - interval '60 days'
   ORDER BY created_at LIMIT $1). Triggered at startup (next to refresh_sweep, 30 s budget) AND at most once per hour
   per instance from POST /error-logs (detached ctx; a request has CPU). The read query also filters
   created_at >= now() - interval '60 days' so the policy holds if the sweep lags. Cloud Scheduler or a Cloud Run Job
   rejected: extra infra plus an auth surface for no gain.
6. Migration numbering rule (record in HANDOFF): A37 takes none. Whichever plan merges first takes 0057; any later
   plan renumbers in the same PR and updates its plan text and PG gate.
7. Delivery: client redactor is web layer, so OTA (make ota-release), no APK. Backend via Cloud Run, no migration.
   Out of scope: webContentsDebuggingEnabled (owner: stays until go-live), keystore note, sharing-archive process,
   A36 backups, transfer PIN in the queue (A08).

## Risks

- Over-redaction hides debugging signal (phone pattern hitting numeric ids): negative vectors + key exemptions.
- TS/Go drift: the shared fixture is the guard; CI fails on mismatch.
- Mutating outbox items while redacting would corrupt retries: deep clone + input-unchanged test.
- Sweep on a big table: batched, advisory-locked, time-boxed, non-fatal.
- Old POS bundles keep sending raw payloads until the OTA lands: server-side redaction covers them from the backend
  deploy onward.
