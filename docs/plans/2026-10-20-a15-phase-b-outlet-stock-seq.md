# A15 Phase B (rebuilt): per-outlet stock counter `outlet_stock_seq`

Date 2026-10-20 · base `prod-hardening` 1bcec7a · planner: Opus (read-only), saved by the main session. **Supersedes Phase B of `docs/plans/2026-10-17-a15-stock-reappear.md` §3** (per-row `stock_seq` fed by a global SEQUENCE + trigger). An advisor review agreed with this design.

## 0. Why the old Phase B is dropped
1. A global SEQUENCE hands out values at UPDATE time but transactions commit in another order: a tablet that stored max = 101 never sees 100 commit later (no reliable "stock changed" signal).
2. A trigger bumping a per-outlet counter would take that counter after the first stock row and before the rest, while a sale takes all its stock rows first and the counter last: a lock-order cycle with transfer send/receive/cancel and stock-count apply (which lock stock rows one per line). Unsafe.
3. Auto-pull (OTA 2.1.4) already heals the old plan's headline case (a pull in flight across this device's own ack: `followUpPull`).
The bug that is really left: **sales and refunds never tell any tablet that stock changed.**

## 1. Already guaranteed (Phase A + settling debits + auto-pull)
Own sales: an acked sale's debit is copied to `settlingDebits` before settle (`engine.ts:1453-1458`, `:1501-1515`); display subtracts unacked, parked and settling entries (`:906-929`); entries retire only when a pull numbered after the ack is applied (`settlingDebits.ts:117-126`). Pull in flight across this device's own ack: entry with `gen >= pullNo` survives and sets `followUpPull` (`engine.ts:559`); auto-pull schedules one more pull (bounded by the 60 s floor, cart gate, 20/h cap). Writers that bump the content version (transfer send/receive/cancel, outlet goods receipt/adjust, stock-count apply, product-create seed) are healed by auto-pull within ~27 s + cart gate. `/sync/pull` and `/sync/version` are uncached; **verified 2026-10-20: `Pull` reads `Version()` FIRST, then `e.Read.Products` through `r.Pool` directly with no cache anywhere in `backend/internal/read/` (the 15 s product cache lives only in the handler layer, which Pull bypasses)** => a pull carrying seq S contains stock committed up to S, so seq-based retirement is safe.

## 2. Residual wrong-stock windows today
R1 another tablet's sale at the same outlet, or a backoffice direct `/orders` sale (`service/order.go:527-532`): HIGH until an unrelated version bump or manual sync. R2 this tablet's own refund restocks on the server (`order.go:950-957`, `RefundTx`, backoffice `RefundOrder`): LOW and nothing triggers a pull. R3 lost response then duplicate ack: the sale is in a pulled snapshot and the duplicate records a fresh entry: LOW, nothing triggers a pull. R4 a review item resolved: debit recorded (`engine.ts:1180-1186`) though head office may not have applied it: LOW. R5 no pulls for days at a quiet single-tablet outlet: entries pile toward the 2000 cap (`settlingDebits.ts:23`) then the oldest drop and stock shows HIGH. R6 pull across own ack: healed (one auto-pull cycle). R7 oversell (A44): same as R1/R3. R8 stock-count apply bumps every outlet's version (wasteful, correct).

## 3. Design D (chosen): per-outlet counter, explicit LAST-statement bump
Ordered by commit (the second transaction blocks on the row lock until the first commits); no gaps (a rolled-back UPDATE consumes nothing); a pull that reads S first then products covers everything <= S (changes above S cause at most one extra pull). Rejected: A per-row seq (gaps), B movement log (needs A17, policy-blocked), C immediate trigger (deadlock).
A42 lock order (extend the comment at `service/order.go:183-196`): `codes -> customer -> stock rows -> order row -> [content_versions rows] -> outlet_stock_seq row(s) in outlet_id order, LAST.` Today no stock-changing transaction touches more than one outlet (send = source, receive = destination, cancel = source); the helper still sorts outlets. Failure mode is benign: a writer that forgets the bump only loses the change signal; it never retires a debit early (own entries carry their own sale's seq).

## 4. Specification
### 4.1 Migration `backend/internal/db/migrations/0057_outlet_stock_seq.sql`
`SET LOCAL lock_timeout = '5s'; CREATE TABLE outlet_stock_seq (outlet_id uuid PRIMARY KEY REFERENCES outlets(id) ON DELETE CASCADE, seq bigint NOT NULL DEFAULT 0, updated_at timestamptz NOT NULL DEFAULT now()); INSERT INTO outlet_stock_seq (outlet_id) SELECT id FROM outlets ON CONFLICT DO NOTHING;` Match the FK behaviour of `content_versions` (`0001_init.sql:347`). Does NOT touch `outlet_variant_stock` (no lock/rewrite on the hot table). The runner applies files by name (`db/db.go:107-125`): on prod 0057 runs after 0063; on fresh/PG-gate DBs before 0058. Additive, forward-only, old revisions ignore the table. Never drop and recreate (resets the seq).

### 4.2 Helper `write.BumpStockSeq(ctx, tx, outletIDs ...string) (map[string]int64, error)`
Dedupe + sort outlets; for each: `INSERT ... VALUES($1,1) ON CONFLICT (outlet_id) DO UPDATE SET seq=outlet_stock_seq.seq+1, updated_at=now() RETURNING seq` (the upsert covers outlets created after the migration). **Exactly once per transaction per outlet.** Writers that MUST bump (LAST statement before commit; watch writers that call other writers so there is no double bump): (1) sale `service/order.go` `createOrder` after the `processed_keys` INSERT and before Commit (`:726`->`:735`; the conflict path `:729-730` rolls back with no gap; return the seq via a new `CreateOrderSeq`/result struct; `CreateOrder` keeps its signature for the direct handler; the sync seam type at `sync.go:404` changes); (2) refund `RefundTx` at its end (the receipt row is claimed first and only UPDATEd after the effect `service/receipts.go:92-126`, so the bump is still last; backoffice `Refund` `order.go:774-784` goes through it); (3) transfer send (`transfer.go:263-302`) source outlet after `bumpVersionOutlets`; (4) transfer receive (`:316-409`) destination; (5) transfer cancel (`:436-461`) source; (6) outlet goods receipt and outlet adjust inside `bumpOutletTx` (`warehouse.go:95-108`) after the content bump, only for `kind=='outlet'` legs where stock changed; (7) outlet stock-count complete (`stockcount.go:449-453`) after `bumpVersion`, the count's own outlet only; (8) product-create seed (`repo.go:203-214`) after `r.tx`'s bump (needs an `r.tx` variant or post-hook). Must NOT bump (stock unchanged): lazy 0-row inserts (`order.go:485-489`, `lockorder.go:111-117`), par level (`warehouse.go:227-231`), available (`repo.go:361-367`), renames (`repo.go:278`, `import_products.go:358-373`), deletes (`repo.go:304`, `:395`), warehouse-only legs (`noBumpTx`).

### 4.3 Server exposure
New `stockSeq` field: Go `*int64` with `json:"stockSeq,omitempty"` (a plain int64 would drop 0); OpenAPI integer int64, optional, NOT nullable, no `$ref`. `Version()` (`sync.go:114-126`) reads `seq` in the same statement as `version` (subselect, COALESCE 0; lazy-seed path too): `VersionInfo.StockSeq`. `Pull`: `PullBundle.StockSeq` from `Version()`, which MUST stay the first query (add a comment). Batch: `BatchResult.StockSeq` from the existing post-items `Version()` read (`sync.go:320`). Per item: `ItemResult.StockSeq` only for `order` + `ok` AND only when the attributed outlet equals the batch caller's outlet (`processBatch` reads `c.OutletID`; items attributed per item at `:464`). Duplicates carry none (orders replay through `processed_keys`, `order.go:222-228`). Kill switch env `SYNC_STOCK_SEQ=off` omits every `stockSeq` (clients fall back to Phase A + auto-pull). OpenAPI: `SyncVersion` (:1838), `SyncPullBundle` (:1862), `SyncBatchResult` (:2066), `SyncItemResult` (:2040); NO `ProductVariant` change.

### 4.4 Client (`packages/sync`, OTA only)
Snapshot carries `stockSeq` in the bundle; new persisted `pulledForOutlet`. **Hard rule:** every seq rule is off unless `pulledForOutlet` equals the current actor outlet AND the server sent a seq; absent = 'no signal', never 0; a mismatch = 'pull wanted'. `SettlingEntry.seq?` set from `res.stockSeq` in `applyBatch` for `ok` orders whose `outletId` is absent or equals the actor outlet; if the batch has a `stockSeq` but the item has none (duplicate, other outlet) set `followUpPull = true` (R3); same for resolved review items (`engine.ts:1182`, R4). Retirement: `applyPull(g, known, pulledSeq)` keeps an entry only if `e.gen >= g` AND NOT (both seqs present and `pulledSeq >= e.seq`) (makes R6 exact); retire-on-record: skip an entry whose seq <= snapshot seq. `pullWanted()` replaces the three `wall.raised || followUpPull` sites (`engine.ts:582`, `:600`, `:616`), re-evaluated when the timer fires: `'data'` if the wall is raised; else `'stock'` if `followUpPull`; else `'stock'` if server seq < local (DB restore: disable seq rules until the next applied pull); else `'stock'` if unexplained drift `(server - local) > count(entries with local < seq <= server)` (gapless one-per-transaction bumps make the count exact, so own sales do not trigger a pull: fixes R1, R2, R7); else `'stock'` if settling entries >= 200 (housekeeping, R5). Server seq from the latest `checkVersion` (`:652-676`) or batch. Race: a 12 s version poll can land after the server commits this device's sale but before the batch response is processed, which looks like foreign drift: recompute after the flush; the `flushing` recheck (`:622`) already defers. Scheduler (`autoPull.ts`): new `'stock'` kind with its own floor (`STOCK_FLOOR_MS` 300 000) and rolling-hour cap (`STOCK_HOURLY_CAP` 10), separate from the 20/h data budget; any applied pull satisfies both; same cart gate (the bundle carries prices). UI: stock-only pulls do not raise 'Pembaruan tersedia'; existing 'Memperbarui...' shows while pulling. Compatibility: new bundle on old server = Phase A + 2.1.4 behaviour; old bundle on new server ignores unknown JSON fields (verify with a parse test); backend rollback: counter stops, old server omits fields, clients fall back. Load at 90 tablets: <= ~900 stock pulls/h fleet-wide (~0.25/s at ~15 KB); re-measure the production bundle before go-live.

## 7. Risks
Mixing seqs from different outlets could retire a debit early (mitigated by the outlet-match rules on server and client, with tests). A forgotten bump in a future writer leaves other tablets stale only (guard test + ST cases). Commit-time lock wait per outlet is a few ms at 1-3 tablets per outlet; deadlock impossible while the bump is last and sorted; 40P01 is already retried (`writes.go:1006`). A DB restore rolls the seq back: regression guard disables seq rules and forces a pull. More pulls mean more full-snapshot Preferences writes: bounded by the 10/h stock cap. Migration lock: `lock_timeout` 5 s; never touches `outlet_variant_stock`. The client half is the risky part (seq retirement + `pullWanted()`): if it must be cut, drop the seq retirement and keep 'pull when foreign drift'.

## 8. Not in scope
Per-variant seqs; A17 movement ledger; a slim `/sync/stock` endpoint and applying stock while a cart is open; removing redundant content bumps (the stock-count all-outlet bump; the receive bump stays because `PendingCredits` retires on it); warehouse stock; other tablets' sales still offline; any APK change.
