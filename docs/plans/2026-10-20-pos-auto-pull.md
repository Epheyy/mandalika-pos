# Plan: automatic background pull of POS reference data

Date 2026-10-20 · base `prod-hardening` 030527b · planner: Opus (read-only), saved by the main session. Owner request 2026-10-20: the POS should pull new data automatically instead of waiting for a tap on the 'Pembaruan tersedia' chip.

## 0. Corrections found while planning
- The poll runs every **12 s** (`SyncProvider.tsx:197` `engine.start(12_000)`), not 20 s (engine default `engine.ts:1473`).
- The data-version wall has THREE writers: `checkVersion()` (`engine.ts:521-558`), the batch-ack path (`engine.ts:1404-1411`, takes `data.version` from `/sync/batch`), and `resync()` clears it (`:499-504`). The observed 198 -> 199 was the tablet's OWN receive: `ReceiveTransfer` bumps the destination outlet (`backend/internal/write/transfer.go:409`), `processBatch` reads the version after the items (`sync.go:320`), so the ack carried 199 and raised the wall. Stock on screen was already right via `PendingCredits`; only the chip was stale. => the scheduler must be armed from BOTH the poll and the ack.

## 1. How it works today
- `content_versions`: one row per outlet with `version` and per-resource `data_manifest` (`write/repo.go:34-66`). `/sync/version` returns `{version, dataManifest, contact}`; the client ignores `dataManifest`. Wall: `raised = server > snapshot.localVersion()`; `SyncStatus.tsx:108` shows 'Pembaruan tersedia'. `Cart.tsx` gets `wallRaised={false}` (`CashierScreen.tsx:1092`): selling is never blocked; keep it that way.
- `resync()` today runs only at boot (`SyncProvider.tsx:185`), the manual button (`useOfflineData.ts:121`) and the settings 'Sinkronkan' button (`CashierScreen.tsx:1188`). Order: `settling.beginPull()` (A15) -> GET `/api/v1/sync/pull` -> dispose-epoch check -> `setReachable(true)` + `noteContact()` (a 2xx pull is an A05 contact) -> `settling.applyPull(pullNo, known)` (false if a newer pull applied) -> `snapshot.replace()` (A30 PII strip) -> `pending.retire(version)` -> `recomputeCredited()` -> set wall. Gaps: no single-flight; failures throw; does not update `isResyncing`/`lastSyncedAt` (those live only in the hook `useOfflineData.ts:93,121-132`).
- The pull is the full bundle, uncached, uncompressed (no gzip middleware): products (page 100000), categories, bundles, promotions, ALL discount codes, loyalty conditions/settings, app settings, all users with permissions, empty `customers` and `receiveApprovers`; ~10 queries; no per-dataset/conditional variant. Measured 2026-10-20 on the test data: ~14.6 KB per outlet, 0.3-0.7 s (8 products, 2 discount codes, 4 users, 4 promotions).
- Snapshot storage: KV in-memory mirror over Capacitor Preferences, fire-and-forget; every applied pull rewrites the whole snapshot (HANDOFF: watch Preferences write cost) => keep pull frequency bounded. CashierScreen reads `engine.getSnapshot()` every render (`:232-255`); `useOfflineData` polls `getWall()` every 2 s (`:139-151`).

## 2. Design (web layer only -> OTA; no backend change)
### 2.1 Ownership
- The ENGINE owns scheduling: new pure module `packages/sync/src/autoPull.ts` (class `AutoPullScheduler`) with injected `now()`, `random()`, `setTimeout` (fake timers in tests). Engine creates it; `start()` arms it; `stop()`/`dispose()` clear it.
- The APP supplies a gate: `engine.setAutoPullGate(fn: (() => boolean) | null)`. No gate registered = DENY (only CashierScreen enables auto-pull). With `start(..., { flushOnly: true })` (A04 mismatch mode) auto-pull is fully OFF: it must never read the account's outlet data even though `checkVersion` still raises the wall.
- New engine API: `nudgeAutoPull()` (called when the gate flips busy -> idle), `isPulling(): boolean`, `lastPulledAt(): number | null`.

### 2.2 Triggers
Private `afterWallUpdate()` is called from `checkVersion` success, the batch-ack wall write, and every `resync()` outcome. If the wall is raised, auto-pull is enabled and nothing is scheduled, schedule a pull. If the server version rises again while a pull is waiting, the jitter restarts; total wait from first detection is capped at 120 s.

### 2.3 Timing (named constants)
Jitter after a raise 5-15 s random; nudge after the gate turns idle 2-5 s random; floor between auto-pull attempts 60 s from the last attempt start; failure backoff 30 s x 2^n jittered 50-100% capped at 10 min; hard cap 20 auto-pulls per rolling hour (then auto stops, manual still works, log once). Backoff resets on any successful pull (auto or manual) and on the `online` event. 4xx failures (same classifier as `classifyFailure`: account/unauthorized/rejected) suspend auto-pull until a later `checkVersion` 2xx.

### 2.4 When the timer fires (in order)
1. Disposed, auto disabled, `!ONLINE()` or `!isReachable()`: do nothing (next poll/`online` re-arms). Offline is always a no-op.
2. Wall no longer raised (e.g. cashier tapped): drop it.
3. Gate false: mark 'waiting for idle'; re-evaluate on each 12 s tick and on `nudgeAutoPull()`; never spin.
4. `this.flushing`: check again in 3 s (a pull in flight across this device's own sale ack leaves stock LOW until the next pull, the A15 residual, and sales never bump the version, so nothing would heal it). Do NOT wait for an empty outbox (parked/stuck items would starve pulls forever); pulling with items queued is safe because `pendingStockDeltas()` keeps subtracting unacked and parked orders.
5. Otherwise `resync({ shouldApply: gate })`.

### 2.5 Changes to `resync()`
- Single-flight: concurrent callers share one promise. If a manual tap joins an auto pull that ends `deferred`, the manual path runs a fresh pull WITHOUT the gate. Manual button and boot always bypass the gate.
- Re-check the gate after the response arrives: after the dispose-epoch check and `noteContact()`, BEFORE `settling.applyPull()`. If the gate now says busy, discard the response and return `'deferred'` (the used pull number is harmless: `applied` does not move). This closes the 1-3 s window where the cashier adds an item while the pull is in flight.
- Return `'applied' | 'stale' | 'deferred'` instead of void (existing callers ignore it).
- NO new `await` after `applyPull`: `applyPull` -> `replace` -> `retire` -> `recomputeCredited` -> wall must stay one synchronous block (this makes the swap atomic for React). Put a comment on it. Write order is already safe: `Snapshot.replace` writes the snapshot before the version key; a crash between leaves an older version = one extra pull.

### 2.6 The gate (CashierScreen)
Pure function in new `apps/pos/src/cashier/autoPullGate.ts` (CashierScreen is 1309 lines: do not grow it). Allow a pull only when ALL are clear: cart (`state.cart.length`), `isCheckoutOpen`, `isProcessing`, `isSuccessOpen`, `refundOrder`, `refundSale`, `isRefunding`, `showReceive`, `pendingReceive`, `pendingTT` (the TandaTerima prompt after a receive), `pendingFulfillment`, `isAddingCustomer`, `activeAdjustment`. Why defer while the cart has items: cart lines carry the price captured when added; promos/codes/settings are re-derived from the snapshot on every render (`:251-255`); `buildReceiptQuote` stamps `engine.referenceVersion()` at sale time (`:700`), so a mid-cart swap would put a new refVersion on old prices. Wiring: register through a ref in a `useEffect`: `engine.setAutoPullGate(() => isSafeToAutoPull(stateRef.current))`, `null` on cleanup; when the gate goes false -> true call `engine.nudgeAutoPull()` (in the observed transfer case the pull then lands 2-5 s after the TandaTerima prompt is closed).

### 2.7 Interactions
A15 settling debits: correctness unchanged (`beginPull`/`applyPull` handle in-flight/out-of-order pulls); more frequent pulls retire settling entries sooner. Pending transfer credits: a pull can read the version before a concurrent receive commits (credit shows HIGH) but `ackVersion` stays above the pulled version so the wall stays raised and the next auto-pull fixes it. A05: a pull is a 2xx contact via `noteContact()` (a deferred pull still counts); a failed pull does not change reachability (`checkVersion` stays in charge); a locked offline cap does not block pulls. A30: all pulls go through `stripSnapshotPii`. A41: archive built from outbox rows, not the snapshot. Outbox: pulling while items are pending is allowed (step 4); flush first, pull after: no pull starts while `flushing`.

## 3. Server load (30+ outlets, ~30-90 tablets)
- Bumps: sales/refunds/POS customer_create bump NO outlet; transfer dispatch/cancel bump the source, receive bumps the destination; warehouse ops bump that outlet; outlet price edits the listed outlets; product/category/promo/discount-code/outlet/app-setting/loyalty edits and product import bump ALL outlets; stock-count apply bumps ALL outlets (`stockcount.go:450`); backoffice customer CRUD/import/tags/segments bump all outlets but the bundle carries no customers since A30 (pure waste); `customRoles` bumps all outlets though not in the bundle.
- Rate: one global bump -> every tablet pulls once within ~27 s (12 s poll phase + 5-15 s jitter), ~1-4 pulls/s briefly at 30-90 tablets; a burst of edits is capped by the 60 s floor (<= ~1.5 pulls/s fleet-wide) and the hourly cap; the existing `/sync/version` poll is already ~2.5-7.5 req/s fleet-wide. Assumption: 5-20 relevant bumps/day -> 5-20 pulls/tablet/day.
- Verdict: a full pull is acceptable at this scale IF the bundle is modest. T0 measurement 2026-10-20 = ~14.6 KB on test data (threshold 500 KB): ship as designed WITHOUT the manifest filter (T3b). **Re-measure the bundle with realistic production data (product count, bulk-generated discount codes) before go-live; if > ~500 KB build T3b: store `dataManifest` when `checkVersion` sees server == local; on a bump skip auto-pull only when every changed key is in the denylist {customers, customer_segments, customRoles}; version-only bump (migration) or missing baseline = pull; manual always pulls.**
- No server change needed. Later backend slice (backlog): stop global bumps for resources not in the bundle; make a stock-count apply bump only its own outlet.

## 4. UX
`useOfflineData` reads `engine.isPulling()` and `engine.lastPulledAt()` in its existing 2 s poll; `isResyncing = manualResyncing || engine.isPulling()`; `lastSyncedAt` updates whenever `lastPulledAt` advances (auto pulls too). Chip: while pulling (lower priority than review, account, stuck, pending) 'Memperbarui...' blue; otherwise while the wall is raised keep 'Pembaruan tersedia' as a status. Panel: keep 'Sinkronkan data terbaru' as manual fallback; when the wall is raised add one grey line 'Diperbarui otomatis saat keranjang kosong.' No toasts. Update the header comment at `SyncStatus.tsx:1-10` ('the cashier decides when to sync'). The settings sync button (`CashierScreen.tsx:1179-1188`) uses the combined `isResyncing`.
