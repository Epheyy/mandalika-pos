## 1. Design decisions (with justification)

**D1. One parser, on the server: Go stdlib `encoding/csv`.** It handles RFC 4180 quoting, `""` escapes, embedded newlines
and CRLF/LF. It reports `ParseError{Line, Column}` and `FieldPos`. It adds zero new dependencies: no lockfile change, no
A38 scanner delta, no Cloudflare frozen-lockfile risk.

Rejected alternatives:
- **papaparse:** a new npm dependency in the A38 inventory, and a second parser that must agree with the server.
- **SheetJS `XLSX.read`:** makes both reviewed read-path CVEs reachable and weakens the A34E4 footing. It also coerces
  `0812...`/`00123` to numbers.
- **Hand-rolled TS state machine:** still a second parser.

The browser uploads the raw file text; the server parses, validates and reports. **Client `parseCSV` is deleted.**

Wrapper settings:
- **Encoding:** strip a UTF-8 BOM. Invalid UTF-8 is rejected with the file-level message "simpan sebagai CSV UTF-8".
  There is no silent Windows-1252 guess.
- **Delimiter:** detected from the first record, quote-aware, among `,` `;` `\t`. The preview reports which one was used.
- **Quotes:** `LazyQuotes=false`, so a stray quote is a file-level error with line and column.
- **Field counts:** `FieldsPerRecord=-1` with our own check. Trailing empty fields (Excel `;;;`) are allowed. Extra
  non-empty fields are a row error.
- **Whitespace:** no `TrimLeadingSpace`. Only key fields are trimmed: SKU, barcode, phone, email, and Nama for matching.
  Free text (Deskripsi, Catatan) is stored as written, except that an all-whitespace value becomes empty.
- **Line numbers:** physical, from `FieldPos`. A multiline record reports the line it starts on.

**D2. Preview is a server dry run of the same code path.** Each kind gets one endpoint, `POST .../import`:
- `dryRun:true` runs parse → validate → plan against current DB state inside a read-only transaction and returns the report.
- `dryRun:false` re-runs everything and applies it.

Both modes share one function, `plan(ctx, tx, rows)`, so preview and commit cannot drift. The server is the authority by
construction. Nothing from the client is trusted except the raw text and options.

**D3. All-or-nothing per import, with idempotency.** Onboarding needs a clean, known state. Partial apply leaves
"which rows went in?" ambiguous and makes re-uploads create duplicates.

The commit sequence:
1. The request must carry an `Idempotency-Key` header, plus the preview's `fileSha256` and `expectedSummary`.
2. Inside one tx, take a transaction-scoped advisory lock (`pg_advisory_xact_lock`) keyed on the string
   `csv-import:KIND`, then re-plan.
3. If the file hash or summary differs from the preview, return **409 `import_stale`** ("data berubah, pratinjau ulang").
4. If any row has an error, return **422** with the same row report and write nothing.
5. Otherwise apply with set-based SQL, run **one** `bumpVersion` per resource, record the `import_runs` row, and commit.

Replays:
- Same key, same hash: return the stored result (200).
- Same key, different hash: 409.

Rows are never dropped silently. Every input row appears in the report as one of create, update, skip or error, and every
skip carries a reason, e.g. "pelanggan sudah ada" or "tidak ada perubahan".

**D4. Row report format.** Preview, 422 and replay all share this shape:
```
ImportReport {
  kind, delimiter, fileSha256, totalRows,
  summary    { create, update, skip, error, warning, newCategories },
  fileIssues[] { severity: error or warning, code, message, column? },
  issues[]   { row, line, column?, severity, code, message, value? },  // ALL errors+warnings, capped at 5000 (then fileIssue too_many_issues)
  rows[]     { row, line, action, key, reason? },                       // first 500 rows only (preview table); counts are exact
  runId?, appliedAt?                                                    // commit/replay only
}
```
- `row` is the 1-based data-row index; `line` is the physical line.
- Messages are in Indonesian. `code` is stable, for tests and translation.
- The client can download `issues` as an "error report" CSV, built with the sanitizing exporter.

**D5. Duplicates and matching** (project rules: never auto-merge; phone dupes are soft).

*Customers:*
- **Key:** the phone after format-only cleaning. Spaces, `-`, `.`, `(` and `)` are removed and a leading `+` is kept.
  There is no +62 to 0 rewrite, which stays consistent with the existing exact-match lookup.
- **Matching:** live rows only (`merged_into IS NULL`).
  - 0 matches: `create`.
  - 1 match: `skip` with reason "sudah ada" (default; see owner Q2).
  - 2 or more matches: `skip`, plus a warning pointing to the Duplikat tab.
- **Same phone twice in the file:** error on the second and later rows.
- **Phone checks:**
  - Scientific notation (`6.28E+11`) is an **error**.
  - A phone not starting with `0` or `+` gets a warning ("angka 0 di depan hilang?").
  - An invalid email format gets a warning.
- **Creates never merge anything.**

*Products:*
- **Product key:** trimmed, case-insensitive `Nama`+`Brand`. Brand is **required** with no default, because this is a
  3-brand template.
- **Variant key:** SKU within that product.
- **Row errors:**
  - An explicit barcode, or the SKU used as barcode, already belongs to another variant (global `idx_variant_barcode`).
    The dry run catches this; it never surfaces as a 23505.
  - The SKU exists on a **different** product (owner Q4).
  - Duplicate SKU, barcode or Ukuran within one product in the file.
- **Size rename:** a matched SKU with a different `Ukuran` is a rename. It moves the `outlet_variant_stock` and
  `outlet_variant_price` rows, as `UpdateProduct` does, and the preview shows a warning.
- **Conflicting product-level cells** across rows of the same product give a warning; the first row wins.

*Ingredients:*
- Match by SKU (globally unique), else by case-insensitive name.
- 2 or more name matches: error (ambiguous).
- Duplicate in the file: error (today it is skipped silently).

*Categories and ingredient categories:*
- Case-insensitive name match.
- Missing ones are created inside the same tx and counted in `summary.newCategories`.

**D6. Merge-only writes that never touch stock.**
- Import never deletes a product, variant, category, customer or ingredient.
- Import never writes stock (`outlet_variant_stock.stock`, `product_variants.stock`), images, `isFavourite`, per-outlet
  price/availability, points or aggregates.
- **On update,** a blank optional cell means "keep the existing value". The templates say so; clearing a field is done in
  the UI.
- **On create,** blanks take the documented defaults: Jual and Aktif = Ya, Unggulan = Tidak.
- Initial stock is loaded by goods receipt or stock count (owner Q1).

**D7. Value parsing.** Each parser is one tested Go function. An ambiguous value is a row error, never a guess.
- **`parseRupiah(s, allowFraction)`:**
  - Accepts `150000`, `150.000`, `150,000`, `Rp 150.000`, `Rp150.000` and `1.250.000`: strict 3-digit grouping with a
    single separator kind.
  - Rejects blank (for required fields), negatives, mixed separators and groups that are not 3 digits.
  - Product price must be an integer, 0 or more; 0 gets a warning.
  - Ingredient `Biaya Default` (allowFraction) also accepts `12,5` or `12.50` (1-2 fraction digits). `1.234` is read as
    grouping, i.e. 1234.
- **Dates** (`Tanggal Lahir`, `Anniversary`): `YYYY-MM-DD`, `DD/MM/YYYY` or `DD-MM-YYYY`, checked against the real
  calendar. Anything else is an error.
- **Booleans:** Ya, Tidak, Y, T, true, false, 1, 0, case-insensitive. Anything else is an error.
- **Length caps:** Nama up to 200, Deskripsi/Catatan up to 2000, SKU/Barcode up to 64. Values over the cap are errors,
  never truncated.
- **Apostrophe reversal (round-trip):** if a cell starts with an apostrophe and its second character is one of
  `=`, `+`, `-`, `@`, tab or CR, strip exactly that one apostrophe before validation. This is the inverse of D8.

**D8. Formula-safe export (every CSV export).** `sanitizeCell(v)` applies to **string values only**. Numbers and
booleans pass through unchanged, so negative amounts and stock deltas stay numbers.

The OWASP CSV-injection rule, adapted:
- Prefix an apostrophe when the string starts with `=`, `@`, tab or CR.
- Also prefix an apostrophe when it starts with `+` or `-` **and** is not a plain number (regex `^[+-]?\d+([.,]\d+)*$`).
  Phones like `+6281234...` and strings like `-5000` stay readable, while `-2+3` or a `+...` command payload is
  neutralized.
- Quote fields that contain a comma, semicolon, double quote, CR or LF. Join records with CRLF (RFC 4180) and keep the BOM.

**XLSX: no prefixing.**
- SheetJS `json_to_sheet` writes plain string cells (type s, no formula), which Excel does not evaluate.
- Prefixing would corrupt values and break the `BO-PAGES-XLSX` typed-text-cell gate.
- Instead, a test asserts that no exported cell has an `f` key.
- `exportToXLSX` keeps its API.

**D9. Limits, auth, audit.**
- **Size limits:** the body cap is 20 MiB (`http.MaxBytesReader`), with an explicit **413**. The CSV text may be up to
  16 MiB, 50,000 data rows and 40 columns; anything larger is a file-level error. This is sized for a 30k+ customer
  onboarding.
- **Time:** apply uses `unnest`-array set-based statements, so it stays well inside Cloud Run's 300 s default.
- **Routes:** one per kind, inside the existing permission groups. The global per-IP rate limit applies.
  - `POST /api/v1/customers/import` (`manage_customers`)
  - `POST /api/v1/products/import` (`manage_products`)
  - `POST /api/v1/ingredients/import` (`manage_inventory` + `RequireRecipesEnabled`)
- **Audit:** migration **0055** adds `import_runs`. Columns: id, kind, `idempotency_key` UNIQUE, user_id, file_name,
  file_sha256, delimiter, total_rows, summary jsonb, status (`applied`), created_at, and result jsonb (the stored report,
  for replay). The handler also writes one `slog.Info` line. Dry runs are not persisted, and raw file contents are never
  stored.

**D10. Non-goals:**
- XLSX import (the A38 read-path reason above).
- Customer opening points or aggregates (owner Q3).
- Customer tags (later; `customer_tags` exists).
- Users and categories CSV import (Phase 5).
- POS/APK changes: none. The POS picks up the result through the normal `content_version` resync.

## 2. Wire contract (OpenAPI to generated types)

`backend/api/openapi.yaml` gets three operations, `importCustomers`, `importProducts` and `importIngredients`.

**Request:** they share `CsvImportRequest { csv: string, fileName?: string, dryRun: boolean, fileSha256?: string,
expectedSummary?: ImportSummary }`. The `Idempotency-Key` header is required when `dryRun=false`.

**Responses:**
- 200 `ImportReportResponse { data: ImportReport }`: preview, applied, or replay.
- 409: `import_stale` or idempotency-key conflict.
- 413: body over the cap.
- 422 `ImportReportResponse`: row errors; nothing applied.
- 403: missing permission.

**Codegen and client:**
- The JSON envelope keeps these operations in the oapi-codegen path.
- Regenerate with `make -C backend gen`, which produces `api.gen.go` and `packages/api/src/schema.d.ts`.
- Add `importCustomers`, `importProducts` and `importIngredients` to `packages/api/src/client.ts`.
- Mind the `$ref`+`nullable` codegen gotcha: optional fields use omit, not null.

## 5. Risks

- **Excel realities.** Users will hit ANSI-encoded "CSV" files, semicolon delimiters, phones turned into `6.28E+11` and
  dropped leading zeros. The UTF-8 rejection with a hint, delimiter detection and phone-shape errors/warnings mitigate
  this, but users still need the RUNBOOK note.
- **Size rename via CSV moves stock rows.** A wrong SKU reused in a file could rename the wrong variant. The preview
  warning and a gate case cover it, and owner Q4 limits the blast radius.
- **Large single transaction.** A 50k-row import on the Neon free tier is one transaction. Set-based SQL keeps it to
  seconds, and the gate measures 30k rows. If Neon struggles, fall back to `CopyFrom` into a temp table in the same tx;
  all-or-nothing stays.
- **Spurious stale checks.** The stale check compares summary counts, not every row, but can still fire if customers are
  created at the POS between preview and commit. That is acceptable: the user just re-previews.
- **Blank means keep.** Import cannot clear a field. This is deliberate and documented in the template and the RUNBOOK.
- **Removed client-side import paths.** T11 and T12 change the UX for the Users and Kategori screens (owner Q5).

## 6. Owner questions (only those that change the design)

1. **Initial stock in the product import?** Default **no**. Stock is loaded by goods receipt or stock count, so the
   movement ledger and Inventori stay the stock authority. A yes needs a per-outlet column design and a ledger movement
   type, and moves the work into the stock tier.
2. **Customer whose phone already exists:** default **skip and report**. The alternative is to fill that customer's
   blank fields when there is exactly one live match. Neither option ever merges.
3. **Opening loyalty points or totals for imported customers?** Default **no**. A yes means append-only points-ledger
   entries (A20-A22 territory) and needs loyalty switched on.
4. **Product rename by import:** default **no**. A SKU already on a different Nama+Brand is a row error, and renames are
   done in the product form. A yes makes SKU the product-identity key.
5. **Users CSV import:** default **retire**. The alternative is to harden it: required password checked by the policy,
   plus a role allow-list.
