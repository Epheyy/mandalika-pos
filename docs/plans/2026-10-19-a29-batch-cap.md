# A29 batch cap: plan (2026-10-19)

## Scope
A29 (AUDIT_REPORT.md:472) is "Mostly done" per docs/audits/2026-10-14-audit-status-sweep.md:297. The gap: `SyncEngine.flush()` posts the WHOLE
outbox to `POST /api/v1/sync/batch` (packages/sync/src/engine.ts ~822-868). The server accepts any array length and body size:
`decodeBatchEnvelope` in backend/internal/handlers/batch_envelope.go has no `MaxBytesReader`, while `syncBatch` in handlers/writes.go (~1487) does.
Client timeout 30 s (`BATCH_TIMEOUT_MS`) = server WriteTimeout 30 s (cmd/server/main.go:84), so a large backlog can time out and resend forever.

In this slice: client chunking + drain, server array cap and byte cap returning 413, large-queue tests.
NOT in this slice (A29 stays OPEN, do not mark resolved): client honouring Retry-After, default deadline for non-batch calls, sanitised/coded errors on
direct handlers and whole-batch errors, per-operation work budget.

## Caps (owner may adjust; defaults accepted 2026-10-19 by the session lead)
- Client: `export const BATCH_MAX_ITEMS = 25` in engine.ts.
- Server: `maxSyncBatchItems = 200`, `syncBatchBodyLimit = 8 << 20` (same as `reviewReportBodyLimit`, handlers/sync_review.go:20). Over either: 413 "batch too large".
- Server caps sit well above the client chunk on purpose: APK 2.1 tablets still send the whole queue. 413 is already in `BODY_REJECT_STATUSES` (engine.ts:153,
  commit 1b432ee, 2026-10-10, before APK 2.1), so an old client falls back to the one-item-per-request isolation path in `onBatchFailure` (slow, lossless).
- No migration.

## Design rules (load-bearing)
1. Snapshot `pending()` ONCE per flush and post in order in slices of `BATCH_MAX_ITEMS`. Never re-read `pending()` between chunks (A15 settling-held orders stay
   pending and would be resent in the same flush). Items enqueued during the flush go out next tick.
2. **REVISED after Opus review (65fa140).** Original rule (stop draining after any retryable error) was WRONG: retryable failures never burn attempts, so one stuck
   item at position <25 would block every later sale/refund forever. Correct rule: STOP the drain only after a thrown/transient failure or the isolation path.
   After a result with status `error` and `retryable !== false`, KEEP draining but EXCLUDE shift_close/shift_open from every later chunk (they stay pending).
   Reason: `processBatch` (backend/internal/sync/sync.go:233-246) only holds shift items behind an earlier retryable failure IN THE SAME REQUEST.
   Known pre-A29 exposure kept: a persistently retryable shift_open lets the new shift's orders/cash_flows go out shift-less (attribute.go:276-279); follow-up.
3. Check `this.disposed` and `ONLINE()` between chunks. Keep `flushing = true` for the whole drain; the `finally` block (emitDeadLetters / emitStuckRetrying /
   checkInReviews) runs once.
4. Return the merged `BatchResult` (concatenated results, last `version`, summed `processed`). `onBatchFailure` receives the failing chunk only.
5. Server: `batchObject` maps every decode error to `errBatchEnvelope`; a `MaxBytesReader` overflow must be detected with
   `errors.As(err, new(*http.MaxBytesError))` and passed through (else it comes back 400). Check array length right after `json.Unmarshal(raw, &entries)`,
   before any per-item decode or dispatch.
