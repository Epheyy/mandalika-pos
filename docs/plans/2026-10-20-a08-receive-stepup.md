# A08 plan: online step-up approval for transfer receive

Date 2026-10-20 · base `prod-hardening` a163d61 · planner: Opus (read-only), saved by the main session.
Owner policy (HANDOFF 'Decisions (owner)' 2026-10-17 item 6): receiving is NOT approvable offline; approval becomes an online step-up; PIN hashes are no longer shipped to tablets; the raw PIN is removed from the queued payload; lockout is enforced on the server. Also closes the slice-9 follow-up "transfer PIN stays in the queued item (follow-up: one-time server approval)".

## 1. How it works today (verified)
- Each user has a receive-approval PIN: `users.receive_pin_hash`, `receive_pin_set_at` (migration 0017). Admin sets via `PUT /users/{id}/receive-pin` (`handlers/users.go:130` `SetUserReceivePin`, admin-only route `server.go:330`); server only checks 4-8 chars (not digits). Hash = `auth.HashPassword` argon2id m=64MiB t=1 p=4 16-byte salt (algorithm fine; weakness is the 10^4..10^8 keyspace once the hash leaves the server).
- Who can approve: admins, plus roles in `app_settings.receive_approver_roles` (default `{}`); a non-admin approver must have `users.outlet_id` equal to the destination outlet (`read/repo.go:927` `ReceiveApprovingUsers`, `sync.go:698` `approverAllowed`, `sync.go:714` `receiveScope`).
- Hashes shipped: `sync.go:209-213` `Pull` puts `receiveApprovers: [{userId, displayName, receivePinHash}]` in every outlet pull (OpenAPI `ReceiveApprover` `openapi.yaml:2312`); POS stores it in the snapshot (`mandalika.pos.snapshot`, debuggable storage).
- On-device check: `apps/pos/src/cashier/receive/PinStepUpModal.tsx:59` `verifyPin(pin, approver.receivePinHash)` (`packages/sync/src/pin.ts`, hash-wasm). Lockout local only (`packages/sync/src/lockout.ts`, 5 failures then 5 min, KV `mandalika.pos.pinLockout`, resettable on the device).
- Queued: `CashierScreen.tsx:880` -> `engine.enqueueTransferReceive` (`engine.ts:667`) queues `{transferId, items, discrepancyReason, approverUserId, pin}` as `transfer_receive` with an optimistic stock credit. `outbox.ts:143` `stripSecrets` removes the PIN only when an item goes to review/parked; on ack (`outbox.ts:390`) the PIN stays until `prune()`, which can be skipped (`engine.ts:1350`); pending/stuck rows keep the PIN.
- Server check: `sync.go:625-691` runs `UserAuth`, role check, `VerifyPassword(p.Pin, hash)`, `receiveScope`, `write.ReceiveTransfer`. **New finding: `/sync/batch` is a PIN oracle with no lockout** (any cashier JWT can submit guessed PINs; only the global API rate limit applies).
- Merged prerequisites confirmed: A03 (`RECEIVE_CONFLICT_CODES`, `isReceiveConflict` `engine.ts:87`; `forbidden` in `KNOWN_ERROR_CODES` `engine.ts:94` so a non-retryable forbidden goes straight to review and `emitDeadLetters` removes the credit `engine.ts:1400`); A13 (`loadTransfer ... FOR UPDATE` `transfer.go:106` + `guardedStatusUpdate`, gate TR); A11 for this item type: `transfer_receive` is NOT run through `e.keyed`/`operation_receipts`: idempotency is `transfers.received_idempotency_key` inside `receiveTransfer`'s own transaction (`transfer.go:312-338`, `retryBusy`), replay probe `attribute.go:123` uses the same column; A04 `attribute()` runs first (`sync.go:423`); A05 `transfer_receive` deliberately left out of `cappedType` (`offlinecap.go:19-26`, "left to A08"); A30 `snapshotPrivacy.ts` strips data in `Snapshot` constructor/`replace` and Preferences `hydrate` (`storage.ts:110,130`), migration 0061 bumps all `content_versions`.

## 2. New flow (online step-up; single-use approval tied to one receipt)
1. Cashier counts in `ReceiveTransferPanel` (cached inbound list still works offline), taps "Setujui".
2. POS creates the receipt key up front with `engine.newReceiveKey()` -> `{orderUuid, idempotencyKey}`; the modal keeps it across retries.
3. Modal fetches approvers online: `GET /api/v1/sync/receive-approvers` -> `[{userId, displayName}]`, scoped to the caller's JWT outlet with exactly the `ReceiveApprovingUsers` rules minus the hash. If offline: modal shows "Persetujuan penerimaan butuh koneksi internet."; no outbox item is created; counts stay only in the open panel; receiving waits until online.
4. Cashier calls `POST /api/v1/sync/transfer-receive-approvals` with `{transferId, idempotencyKey, items[], discrepancyReason, approverUserId, pin, deviceId}`. Server: coarse per-IP limit first (own `mw.RateLimit` bucket e.g. `"pinstep"` 20/min; argon2 uses 64 MiB per call); checks the transfer exists (404), destination is the caller's outlet (403), `transferTransition(status,"receive")` allows (409); opens one transaction and runs the lockout steps (section 3), lockout checked before argon2; loads the approver, checks eligibility and PIN. Unknown, ineligible, no-PIN and wrong-PIN all return the SAME 403 "PIN salah atau penyetuju tidak berwenang". On success upserts a grant row `UNIQUE(outlet_id, receipt_key)` (a re-mint for the same key re-verifies the PIN, counts as an attempt, refreshes the row). Grant stores: `fingerprint` = sha256 over canonical form (transferId, items sorted by productId|variantSize with receivedQty, trimmed reason; computed in Go only, at mint and at redemption), `requested_by` (JWT user), `outlet_id`, `device_id` (advisory), `approver_id`, the approver's `pin_set_at`, `issued_at=now()`, `expires_at=now()+TTL`. Returns 201 `{approvalGrantId, expiresAt, approverUserId, approverName}`.
5. POS calls `enqueueTransferReceive({orderUuid, transferId, items, discrepancyReason, approvalGrantId})` with NO PIN, then optimistic credit and flush as today. `approvalGrantId` is not a bearer secret (it only completes the receipt with this exact key, outlet, requester and fingerprint, once); it stays an id for redaction (`isIdKey`); `pin` is already in `SECRET_KEYS` in both redaction twins.
6. Redemption in the batch item (`sync.go` `transfer_receive` case), in order:
   a. Replay first (NEW): `e.replay(...)`; if the key already landed (via `received_idempotency_key`) return ok/duplicate before any grant/authority check (a landed receipt keeps replaying after the grant expires, the PIN is re-set or the approver demoted).
   b. Decode payload; if `approvalGrantId` missing (legacy PIN item or scrubbed item) return Forbidden "Persetujuan online diperlukan" -> review with counts kept.
   c. `write.ReceiveTransfer(..., ReceiveMeta{..., Approval: &ApprovalBinding{GrantID, OutletID: c.OutletID, RequesterID: c.UserID, ReceiptKey: it.IdempotencyKey, Fingerprint}})`. Inside `receiveTransfer`, after `loadTransfer FOR UPDATE` and after the completed/same-key early return:
      `UPDATE transfer_receive_approvals SET consumed_at=now(), consumed_key=$key WHERE id=$1 AND outlet_id=$2 AND requested_by=$3 AND receipt_key=$4 AND transfer_id=$5 AND fingerprint=$6 AND consumed_at IS NULL AND expires_at > now() RETURNING approver_id, pin_set_at`.
      No row -> a diagnostic SELECT picks the message: kedaluwarsa / sudah dipakai / tidak cocok / tidak ditemukan; all `apperr.Forbidden`, non-retryable. Then re-check the approver in the same transaction: user still exists, still passes `approverAllowed` and `receiveScope`, and `users.receive_pin_set_at` equals `grant.pin_set_at`; else Forbidden "Persetujuan dicabut". `received_by` comes from `grant.approver_id`, never the payload. Lock order: transfer row, then grant row.
   d. Device mismatch (`env.DeviceID != grant.device_id`) only `slog.Warn` (advisory).
   Every refusal is `forbidden` (old and new POS bundles already send it straight to review); no new error code; nothing dropped; head office resolves review items.
- TTL vs the A05 12 h cap: default TTL 12 h from mint, server clock at both ends. `transfer_receive` stays out of `cappedType`; the TTL is its bound. Update the comment at `offlinecap.go:19`.

## 3. Lockout (Postgres is the authority, A33; Redis only the coarse IP bucket)
- Keys: `receive_pin_lockouts(subject_kind in {approver, requester}, user_id)`, independent of IP.
- Mint transaction: (1) `INSERT ... ON CONFLICT DO NOTHING` rows; (2) `SELECT ... FOR UPDATE` in fixed order (approver, then requester) to serialize parallel guesses; (3) if either is locked return 429 with `Retry-After`, record `locked`, skip argon2, commit; (4) verify PIN; (5) on failure update both counters (unknown approver counts against the requester only); (6) on success reset both.
- Policy (pure `nextLockout(state, now, outcome, params)`, table-tested), defaults: approver 5 consecutive failures lock 15 min, doubling per cycle up to 24 h, hard lock after 3 cycles until an admin acts; requester 10 failures, same doubling, no hard lock.
- Unlock: time (except hard lock); admin re-sets the PIN via `PUT /users/{id}/receive-pin` (now also clears that user's lockouts and implicitly revokes outstanding grants because `pin_set_at` changes; add server-side digits-only validation `users.go:144`); new `DELETE /api/v1/users/{id}/receive-pin-lockout` (admin group) clears both kinds without changing the PIN.
- Audit: append-only `receive_pin_attempts(at, outlet_id, requester_id, approver_id NULL, transfer_id, device_id, outcome in granted|wrong_pin|ineligible|locked|reset)`; PIN never stored or logged. Grant rows are the audit trail for successful approvals.
- HTTP: 400 invalid body; 403 uniform message; 404 transfer not found; 409 not in transit; 429 `Retry-After` + "Terkunci, coba lagi dalam N menit"; 503/500 per `writeErr`.

## 4. Stop shipping hashes; clean up tablets
- Server: `Pull` sets `ReceiveApprovers = []api.ReceiveApprover{}` (field kept so old bundles parse; `ReceiveApprovingUsers` no longer called in Pull); `ReceiveApprover` becomes `{userId, displayName}`; `UserAuth` stops returning the hash to sync.
- Old POS on the new server: after its next pull `receiveApprovers` is `[]` -> `PinStepUpModal.tsx:84` shows "Belum ada penyetuju ber-PIN ... Hubungi admin": receiving blocked, nothing breaks (acceptable, matches policy) until the OTA lands. Do NOT keep entries with the hash removed (old POS would `verifyPin(pin, undefined)` -> "PIN salah" and burn its local lockout). Until that pull an old POS can still approve locally but the new server refuses those items (no grant) -> review.
- Migration 0062 bumps `content_versions` so old bundles re-pull promptly and overwrite cached hashes.
- Purge on new POS: extend `hasSnapshotPii`/`stripSnapshotPii` in `packages/sync/src/snapshotPrivacy.ts` to force `receiveApprovers: []` (covers `Snapshot` constructor/replace and `storage.ts` hydrate incl. legacy localStorage lift); remove KV `mandalika.pos.pinLockout` at boot (`apps/pos/src/main.tsx`, next to the A30 cleanup).
- Hashes already leaked: every receive PIN hash has sat on tablets in debuggable storage and a 4-digit PIN falls quickly offline. Owner Q1: clear every receive PIN (`receive_pin_hash`, `receive_pin_set_at` -> NULL) so admins set new ones. **DECISION (main session): the wipe is its OWN migration `0063_receive_pin_wipe.sql`, separate from 0062, so the owner can approve or drop it at release without touching the schema migration; default recommendation = apply it.** No hash-format migration needed (argon2id stays).
- Raw PINs in queued items at upgrade: new `Outbox.scrubLegacySecrets()` via `mutate`/`commit` (writes the journal) strips `payload.pin` from every `transfer_receive` row in any status (incl. acked not yet pruned), leaving seq/status/attempts/key untouched; engine `start()` calls it once after the outbox loads (best effort, retried next boot). A still-pending legacy item then goes out without PIN or grant, gets `forbidden`, lands in review with counts kept, credit removed; the physical receipt is never dropped. Release rule (backend first, tablets at 0 pending) should leave nothing to scrub. Caveat: SQLite free pages may keep old bytes until VACUUM (out of scope).
- Dependencies: delete `pin.ts`, `pin.test.ts`, `lockout.ts` + test and the `index.ts` export; `hash-wasm` stays (used by `journalBoot.ts`): NO package.json/lockfile change.
