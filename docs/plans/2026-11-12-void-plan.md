# Void ("Batalkan transaksi") Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a cashier or a `void_any` user void a wrong sale (whole sale, mandatory reason) and record its replacement in its place, with stock, points, codes, customer stats, shift money (including closed shifts) and the ERP made right, and every step kept in an append-only audit record.

**Architecture:** The void gets its own Go write path, `service/void.go`. It never writes `order_refunds` and never calls `RefundLinesTx`. It sets `orders.status='cancelled'` and writes one append-only `order_voids` row.
- **Stock.** The return is driven by the sale's own ledger movements (`stock_movements` kind `sale`, giveaway included). It is recorded as a new ledger kind `void`.
- **Atomic replacement.** A void and its replacement run in ONE transaction:
  - on the tablet's `/sync/batch` path, as one new outbox item type `void`;
  - on the Backoffice path, as one `POST /orders/{id}/void`.
  - Both use a transaction-owned sale core (`createOrderTx`).
- **Closed shifts.** The close snapshot is never touched. Corrections are append-only per-method rows in `shift_corrections`.
- **ERP.** Until Phase 5, the ERP documents that a void creates or depends on are parked in `erp_outbox` as `held`, under hold reason `void_erp_pending`.

**Tech Stack:** Go 1.26.11 (pgx, chi, oapi-codegen), PostgreSQL, OpenAPI 3 → openapi-typescript, React + Vite (POS on Capacitor, Backoffice), vitest.

**Spec:** `docs/plans/2026-11-12-void-design.md` (owner-approved 2026-11-12). Builds on `docs/plans/2026-11-12-bundles-design.md` and `docs/plans/2026-11-12-bundles-plan.md`.

## Design deviations found (code vs design)

1. **No "cashier preset" exists in code.** Presets are `custom_roles` rows: user data, created via `write/stockcount.go:37`, and imported by fsmigrate. A new user starts with no permissions (`apps/backoffice/src/screens/users/AddUserModal.tsx:68-75`).
   - **Resolution:** migration 0092 grants `void_own_shift` to every `role='cashier'` user. It also adds the permission to every custom role whose name matches `kasir|cashier` (case-insensitive). AddUserModal pre-ticks `void_own_shift` when the role is `cashier`.
   - See owner decision O1.
2. **The append-only audit row can't carry "menunggu pengganti" → "pengganti dibuat / tanpa pengganti".** Both are later writes.
   - **Resolution:**
     - `order_voids` is insert-only, enforced by a trigger.
     - A later replacement or a "tanpa pengganti" mark is one row in an insert-only `order_void_followups` table (one per void).
     - The replacement order carries `orders.replaces_order_id`, which is UNIQUE.
3. **The giveaway is not an order item** (`service/ledger_hooks.go:151-189`, dedupe key `giveaway:<orderId>`). `RefundLinesTx` restocks only `order_items` (`service/refund.go:185-205`), yet the design says the giveaway counts.
   - **Resolution:** the void restocks exactly the sale's ledger movements (`kind='sale' AND ref_type='order' AND ref_id=<order>`), which include the giveaway. That data source also skips lines the sale never moved (`unresolved_variant`, legacy `is_bundle`) for free.
4. **The ERP relay kills unknown kinds.**
   - `ErrUnknownKind` → `statusDead` (`integration/erp/relay.go:263`, `payload.go:38-41`).
   - The `kind` CHECKs on `stock_movements` (`0064:13`) and `erp_outbox` (`0065:21`) do not allow a new kind.
   - The ledger enqueues every document part automatically (`ledger/ledger.go:304-345`, `ledger/outbox.go:39-45`).
   - **Resolution:** decision E below (hold until Phase 5).
5. **The movement summary counts `cancelled` orders as refunded units** (`read/inventory.go:327-336`, the legacy whole-order rule). Runtime voids would land there and be counted wrongly.
   - **Resolution:** that branch excludes orders that have an `order_voids` row. A new branch adds the units each void restocked, dated at `voided_at` (Task 1.6).
6. **The opname choice cannot be made offline.** The tablet has no stock-count data.
   - **Resolution:**
     - Online, the POS shows the choice from `GET /orders/{id}/void-preview`.
     - Offline, it sends no choice. Restocking a counted item without asking would correct stock twice (an anti-goal).
     - So when a completed stock count covers an item and the item carries no per-item choice, the server refuses the void with `ErrVoidCountNeedsChoice`, a review reason that says "lakukan online". The sale stays completed. See O6.
     - The sync payload therefore carries `stockChoices` (every line the preview listed as counted), not only the skipped keys.
7. **There is no expected-cash or "Selisih" figure in the `Shift` schema or the Backoffice** (`packages/api/src/schema.d.ts:4756-4802`, `screens/reports/shiftReport.tsx`). The POS computes it on the device.
   - **Resolution:** the server returns the original snapshot buckets plus `corrections` (per-method deltas) and the `corrected*` buckets.
   - The Backoffice shows Asli / Koreksi / Setelah koreksi per method. `closingCash` and `countedByMethod` are shown unchanged.
   - No new expected-cash formula is invented.
8. **The Backoffice refund gate is admin-only** (`apps/backoffice/src/screens/Orders.tsx:130`), not `process_refund`.
   - **Resolution:** void UI gates on `void_any` through a new `canVoidAny(user)`. The refund gate is not copied.
9. **`packages/types/src/index.ts:28-34`:** `OrderStatus` says `cancelled` is "never written by runtime code", and it lacks `partially_refunded`.
   - **Resolution:** add `PARTIALLY_REFUNDED` and fix the comment (Task 3.1).
10. **`point_transactions.type` CHECK** (`0031_points_ledger.sql:9`) and the OpenAPI enum (`openapi.yaml:~1105`) lack a void type.
    - **Resolution:** add `'void'` (migration 0092, OpenAPI, Backoffice `pointTypes.ts` label `Pembatalan`).
11. **The sale core owns its transaction.** `createOrderCore` begins and commits (`service/order.go:260,841`) and replays through the pool (`:869-878`), so it cannot join a void's transaction.
    - **Resolution:** Task 2.2 extracts `createOrderTx`.
12. **Unsynced sales are not in the POS history.** History is server-only; queued sales live in `LocalReceiptsPanel` (`apps/pos/src/cashier/LocalReceiptsPanel.tsx`).
    - **Resolution:** Batalkan also appears on a local receipt. The void names the sale by `saleOrderUuid`, resolved server-side the way refunds do it (`sync/sync.go:151-197`), and the engine holds it until the sale is acked.

## Decisions taken here (builder-level, from "Left to the builder")

- **A. Penyesuaian koreksi.**
  - Stored as `orders.correction_amount` (signed, whole rupiah, default 0) on the replacement. Negative means the store received less than the corrected price; positive means it received more. It is not stored as a manual discount or surcharge.
  - The server computes it from `CorrectionTarget`, so `finalTotal = target`. `allocateOrderLines` then spreads it over the line nets.
  - It never earns or costs points: `points_earned` is computed before the adjustment.
- **B. Amounts.**
  - **Editable:** only when the void is `own_shift` from the POS and the original's shift is the open shift.
  - **Forced** `CorrectionTarget = original total` in every other case: Backoffice replacement, "Buat pengganti", a closed shift, or no shift. The replacement's tenders must then sum to the original total.
- **C. After close.**
  - `after_close` = the original's shift is closed when the void commits.
  - **Counted in a closed shift** (`voidCountedInClose`), for an order X on closed shift S, is true when either:
    - `X.created_at <= S.closed_at`, so X was in the snapshot; or
    - X has a `shift_corrections` row with `kind='replacement'`, so X is a replacement already booked as a correction.
  - **−delta (void rows):** written when the voided order's shift is closed at void commit **and** the order is counted.
  - **+delta (replacement rows):** written when the replacement's shift is closed at its commit **and** the original was not late (`original.created_at <= closed_at`, or the original is itself counted by the rule above).
    - This covers a `later` void made while the shift was open, whose replacement is made after close: no −delta (the cancelled original dropped out of the snapshot by itself), but a +delta.
  - A late original (created after close) was never counted, so voiding or replacing it writes no delta.
  - **Known limit:** any sale transaction in flight across the close (started before `closed_at`, committed after the close read the orders) is misclassified as counted. Accepted; stamping a per-order "counted" flag at close would remove it later.
- **D. Shift lock.** The void takes `SELECT … FROM shifts WHERE id=$1 FOR SHARE` right after it locks the order row, so it serialises with `CloseShiftTx`'s `FOR UPDATE` (`service/shift.go:166-168`).
  - Global order: codes → customers → original order row → shift row → stock rows (sorted) → replacement order insert → `BumpStockSeq` (last, once).
- **E. ERP before Phase 5.**
  - The ledger's enqueue writes `status='held'`, `hold_reason='void_erp_pending'`, with the normal finite `next_attempt_at=now()`, for the documents below. Not `'infinity'`: `admin.go:36,182` scans it into `time.Time`, and pgx errors on Infinity.
  - The relay never claims them: `claimSQL` (`relay.go:95-99`) gains `AND COALESCE(hold_reason,'') <> 'void_erp_pending'`. The documents held are:
    1. every `kind='void'` document;
    2. every document whose `ref_type='order'` names an order with `replaces_order_id IS NOT NULL` (the replacement's sale, and any later refund of it).
  - So the ERP keeps seeing only the original sale until the reversal can be sent.
  - A stockless void has no outbox row. Phase 5 backfills it from `order_voids.erp_document_key = 'void:<voidId>'`.
  - Admin "Retry" refuses `void_erp_pending` rows until Phase 5.
- **F. Replacement idempotency.**
  - **Tablet path:** `orders.idempotency_key = <void item key> + ":replacement"` and `order_uuid = payload.replacement.orderUuid`.
  - **Backoffice path:**
    - `clientVoidUuid` is **required** (400 `clientVoidUuid tidak valid.` when absent or not canonical).
    - `device_id = directRefundDevice(userID, clientVoidUuid)`, the pattern at `handlers/orders.go:246`, so `UNIQUE (device_id, client_void_uuid)` matches on a retry.
    - Replacement key `"bo:" + clientVoidUuid + ":replacement"`.
- **G. Grant timing.** Migration 0092 does **not** bump `perm_version`. The grant reaches a tablet at its next token refresh, within one access-token TTL (15 min). Revocation still works instantly through #138.

## Open owner decisions (defaults built unless the owner says otherwise)

- **O1, who gets `void_own_shift`.**
  - Default: every existing `role='cashier'` user, plus custom roles named like `kasir`/`cashier`.
  - New cashiers get it pre-ticked in "Tambah pengguna".
  - Managers get nothing automatically. Admins have everything.
- **O2, default on the POS when the corrected cart prices differently** from what an own-shift sale received: **"Catat sebagai Penyesuaian koreksi"**. The other choice, "Pelanggan bayar/terima selisih", lets the cashier edit amounts.
- **O3, void window:** default 7 days (design). The bounds of 1–30 days are the builder's call.
- **O4, ERP lag.** Until Phase 5 ships, the ERP keeps the original wrong sale, and replacements and their refunds wait in the outbox as `held`. Default: hold, as decision E. The alternative is sending replacements now and accepting a double sale in the ERP.

- **O5, sales rung in a shift opened offline.**
  - **Verified:** they keep `shift_id NULL` for good. The POS sends `shift.currentShift?.id || null` (`CashierScreen.tsx:930`); the envelope shift is empty while the open is pending (`engine.ts:864`); `attribute.go:229-252` accepts an empty shift.
  - **Default:**
    - The POS blocks Batalkan while the shift's open is still pending sync, as refunds do (`refundView.ts:252`, text `Shift masih tersimpan di tablet`).
    - Once the shift has synced, an unattributed sale (`shift_id NULL`) counts as own-shift only if all of these hold:
      - same outlet as the caller;
      - `orders.device_id` = the item's envelope device;
      - `orders.created_at >= opened_at` of the currently open shift;
      - the envelope shift is that open shift;
      - the caller has `void_own_shift`.
    - `"" == ""` is never own shift.
- **O6, offline void of an item a stock count covered.**
  - Default: refuse with `ErrVoidCountNeedsChoice` (Conflict, non-retryable → review): `Stock opname sudah menghitung barang di transaksi ini. Lakukan pembatalan saat online agar pilihan stok bisa dibuat.`
  - The sale stays completed, and the tablet shows the reason.
  - The alternative (restock and flag) risks correcting stock twice.

## Review Focus

1. **A replacement cart is abandoned, the app restarts or the shift closes before payment.** Nothing is voided, the original stays `completed`, and no `void` outbox item exists. After a restart the replacement cart is gone; it is not restored as a plain sale, which would count the money twice.
   - Tests: `openCartFromState returns null while a void draft is open` and `shift close cancels the void draft` (3.3), `confirm refuses a void draft whose shift is no longer open` (3.3).
2. **An offline own-shift void (with replacement) reaches the server after its shift closed.** Both are refused (`ErrVoidShiftClosed`, forbidden → review), neither is applied, and a later retry with the same key stays refused. The tablet shows the review reason.
   - Tests: `TestDecideVoidAuthorityOwnShiftClosedRefused` (1.3), Postgres `offline_own_shift_after_close_refused` (2.4).
3. **A void of a sale whose earned points were already spent.** The balance floors at 0, `points_forgiven` records the shortfall, and redeemed points are still restored.
   - Tests: Postgres `void_points_spent_floor` (1.4).
4. **A void after an approved stock count covered an item.**
   - Skipped lines are not restocked, and choice `skip_counted` is recorded.
   - A covered line with no choice (an offline void) refuses the whole void (`ErrVoidCountNeedsChoice`, O6), and nothing changes.
   - No line ever restocks twice.
   - Tests: `void_counted_after_skip`, `void_counted_after_choice_missing_refused`, `void_counted_after_restock_chosen` (1.4), `void_preview_lists_counted_lines` (1.5).
5. **A split-tender sale on a closed shift is voided and replaced with another split.**
   - The snapshot columns are byte-identical before and after.
   - `shift_corrections` holds −each original line and +each replacement line per method.
   - The corrected buckets equal snapshot + deltas, and `closing_cash` is unchanged.
   - The same holds for the other two paths: a `later` void made while open and replaced after close gets +rows only; a replacement voided on a closed shift gets −rows.
   - Tests: `TestShiftCorrectionRows`, `TestVoidCountedInClose` (2.1), Postgres `void_replace_closed_shift_deltas`, `closed_shift_snapshot_unchanged`, `later_void_open_replaced_after_close`, `void_replacement_on_closed_shift` (2.3).
6. **The same void is double-submitted, or sent from two tablets.** The same key replays `ok` with the same ids. A different key gets `ErrVoidAlreadyVoided` (review). Stock, points and codes change once.
   - Tests: `void_replay_same_key_ok`, `void_twice_conflict` (1.4).
7. **A void races a refund of the same sale on another device.** The order row lock serialises them, and exactly one commits; the other gets `ErrVoidRefunded` or `ErrOrderNotRefundable`.
   - Tests: Postgres `void_races_refund` (1.4).

- Stockless voids have no outbox row. `order_voids.erp_document_key` names them.
- The ERP admin list shows them under `held`.
