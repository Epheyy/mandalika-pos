# Mandalika POS — A14 Backoffice-generated stock-count template contract

Date: 2026-09-19  
Status: proposed technical contract for Codex design reconciliation; not implemented functionality or production approval.  
Companion: `A04_A14_DESIGN_CLARIFICATION.md`. This document supplements its A14 requirements; it does not replace A04 or resolve its separate authentication questions.

## 1. User decision and scope

The user confirms that imported count files will use a template generated by Backoffice and will adopt the format needed for accurate live-operation and delayed/backdated reconciliation. There is no requirement in this clarification to accept arbitrary third-party spreadsheets or a pre-existing date-only format.

The confirmed business requirement remains: allow counts to be entered/imported while outlets continue selling, including backdated physical observations, with automatic reconciliation when the evidence is sufficient. An upload is an observation, not a command to overwrite current stock.

The choices below are recommended technical defaults. Do not represent them as features already shipped or as independently approved changes to business authority, closed-period policy, or authentication. The reviewed files do not establish the state of any newer, unshared Codex edits.

## 2. Proposed format and Backoffice workflow

Use a versioned, macro-free `.xlsx` template as the primary human-facing import format. This is a transport/UI choice, not the source of reconciliation correctness. Do not require CSV support in the first implementation slice; any later CSV path must normalize into exactly the same validated observation contract.

In Backoffice, an authorized user creates a count session, chooses one inventory location and stock category, chooses the products/variants to count, and identifies the person responsible for the physical count. Backoffice supplies the location timezone, stable identities, units, and schema version. The generated workbook contains an Instructions sheet, a Count Entries table, and machine metadata identifying the registered session/template. The people entering data should not need to type database IDs or stock adjustments.

Default to rolling/per-item observation times. A genuine common snapshot time may be selected explicitly, but must not be auto-populated as the time of export, file creation, or upload. A common physical count date can be explicitly applied to rows to save typing; each row still has an actual observation time unless a valid common cutoff is established.

The same validated observation and reconciliation service must support direct Backoffice entry. Saving a row now is its observation time only when staff are actually recording a just-observed quantity; later transcription requires the actual historical observation time. Do not equate a form's save timestamp with a physical fact by default.

A session may be created after the physical count. Exporting a template today for a count recorded yesterday must be possible when the items/scope/history can be resolved. Today's exported stock/version is not yesterday's baseline.

### Submission workflow

1. Create the session and download its registered template, or enter observations through the equivalent form.
2. Record the physical quantity and actual observation date/time per included row. Optional notes explain unusual circumstances.
3. Upload into a staging/validation view. This step changes no inventory balances.
4. Preview the included observations, uncounted items, errors, historical book quantities, discrepancies, post-count movements, and reconciliation status. Show a calculation revision/as-of indicator.
5. The submitting user confirms the intended submission. This is not a newly imposed manager-approval step. Existing scoped permissions still apply.
6. Persist the validated included observations and submission receipt atomically, then reconcile them under the shared stock-writer protocol. Evidence gaps/conflicts remain explicit per row; ordinary unambiguous rows do not acquire a new manual-approval requirement.

## 3. Generated session/template metadata

The server is authoritative for this metadata. Copying or editing it in a workbook cannot grant access or change scope.

| Field | Proposed contract |
|---|---|
| `schema_version` | Explicit parser/semantic contract; reject unsupported versions with a migration/regeneration message. |
| `template_id` | References a registered export/manifest; not an authorization secret. |
| `count_session_id` | Stable identity for this counting activity, including retries and regenerated downloads. |
| `template_revision` | Links to the exact generated item manifest; versioning is distinct from historical stock coverage. |
| `location_id` / location type | One outlet/warehouse inventory location per workbook by default; never derived only from a typed name. |
| `stock_category_id` | The particular physical inventory category being observed. Sellable on-hand, inspection-held returns, etc. remain separate. |
| `location_timezone` | Configured timezone for this session, retained as historical context, not inferred from the uploader's browser. |
| `generated_at`, `generated_by` | Export provenance only; never default the physical count cutoff from these. |
| `counted_by_reference` | Responsible physical counter selected for the session, with a controlled override path for multiple counters. |
| `capture_mode` | Per-item observation by default, or explicitly established common-cutoff observation. |
| row manifest | Server-issued row identity, product/variant identity, unit/precision and allowed scope for every listed item. |

The original observer and authenticated uploader are different roles. Record both. A selected/typed counter name is attribution evidence, not proof that the person authenticated or granted an approval.

## 4. Count Entries table

All examples below are illustrative field names and formats, not real outlet/catalog values.

| Column | Filled by | Import meaning |
|---|---|---|
| `row_id` | Backoffice | Stable row identity as text; survive sorting/re-export. Do not use spreadsheet row number as identity. |
| `item_id` / `variant_id` | Backoffice | Exact registered item; preserve as text. Names/SKUs are not substitute join keys. |
| SKU / barcode, item name, variant | Backoffice | Human identification; preserve identifier text. Reject ambiguous substitutions rather than fuzzy matching. |
| `unit` | Backoffice | Explicit count unit supported for that item. Do not silently interpret a box as a piece or use today's changed conversion for an old observation. |
| `physical_quantity` | Staff | Actual quantity in the complete specified scope/category. Blank is uncounted; numeric zero is an explicit zero count. |
| `observed_date_local` | Staff | Actual physical observation date, displayed/entered as `YYYY-MM-DD`. |
| `observed_time_local` | Staff | Actual physical observation time, 24-hour `HH:MM[:SS]`; retain supplied precision and do not invent unobserved seconds. |
| `notes` | Staff, optional | Plain-text observation context; not an alternate channel for required structured fields. |

Quantity and date/time cells start blank unless an actual observation/date has explicitly been supplied. Do not prefill physical quantity with book stock or zero. Do not include an editable adjustment or final-stock column. The server calculates these values from retained evidence.

### Values and formatting

- For the first parser contract, generate date/time input columns as text with the stated unambiguous formats and instruct users accordingly. Reject ambiguous locale dates such as `09/10/26`; do not guess. Any later support for native spreadsheet date serials must handle workbook date-system metadata explicitly and pass dedicated round-trip tests.
- Keep IDs, SKUs, and barcodes as actual text cells, not merely numeric cells with a display mask. Microsoft documents that Excel can strip leading zeros or reduce long numeric identifiers to 15 significant digits [E1].
- Accept finite, nonnegative quantity values within the domain's supported range and item-unit precision. Fractional quantities are permitted only for units that support them. No silent truncation or rounding. Define canonical decimal normalization so parsing and hashing do not depend on incidental floating-point representation.
- Count input cells must be literal values, not formulas or cached formula results. Do not use `NOW()`/`TODAY()` to manufacture observation timestamps. Spreadsheet recalculation is not evidence of when staff counted goods.
- Make generated columns visually distinct and protected against accidental edits where supported. Worksheet protection is not an authorization boundary [E2]. Revalidate identities, metadata, scope, and permission on the server.
- Keep the machine table's column keys versioned and unique. Blank inserted rows, safe formatting changes, and row sorting must not alter identity. Duplicate keys, duplicate headers, removed required fields, and malformed row structures fail explicitly.

## 5. Observation scope and physical timing

### Whole scope, not an accidental shelf subtotal

A row observes all of the item within the selected inventory location/category. Counting only one shelf must not overwrite the aggregate stock for the entire outlet. A later supported sublocation/bin feature needs its own nonoverlapping scope and rollup rules. Do not silently sum repeated rows that might be duplicate observations rather than disjoint subtotals.

Physical on-hand observation is not an arbitrary overwrite of a derived available-to-sell figure. Reservations, holds and inspection state must keep their distinct meanings. The count cannot release returned or provisional goods for sale.

### What the timestamp must establish

Keep `observed_at`, entered/imported time, server acceptance time, and reconciliation time separate. Retain the original local text, session timezone, normalized instant where unambiguous, supplied precision, and any cutoff evidence. PostgreSQL stores `timestamp with time zone` as an instant without retaining the originally supplied timezone, so retaining the zone/source context requires separate fields [E3].

A rolling count can take an hour while sales continue, but each item must have a meaningful quantity-at-cutoff observation. If stock moves while that same item is physically being counted, staff must establish whether it was included, normalize the observation using known movements, or recount/review that row. A timestamp to the second does not by itself prove the physical ordering.

Minute-only input is not silently exact to the second. When movement ordering within the supplied uncertainty interval could change the result, retain the observation and mark it for additional evidence/review. A documented physical boundary/normalization can resolve it. Date-only or missing-time input can be retained as an incomplete draft, but must not silently be applied at midnight, shift close, template export, or upload time.

Where available, use the original POS operation-sequence boundary and relevant inventory coverage revision as additional evidence. A sequence from one device does not order independent Backoffice movements. A deterministic sort by UUID is not proof of physical before/after ordering.

## 6. Reconciliation contract

For the latest valid count of a given stock scope, with no later accepted observation and sufficient movement evidence:

    corrected_stock_now = physically_observed_quantity
                          + net physical stock movements after the observation cutoff

The discrepancy at the cutoff is:

    discrepancy = physically_observed_quantity
                  - reconstructed_book_quantity_at_the_same_cutoff

These are explanatory equations, not a complete implementation for multiple counts or late arrivals. Reconciliation needs all stock-affecting operation types, consistent scope/unit semantics, an explainable historical baseline, and coordination with other stock writers. The original A14 dependencies remain in force: movement history, idempotent receipts, projection coverage, stock concurrency and historical-time policy.

### Required examples

**Normal late import:** book quantity at 10:00 is 100; physical observation is 80. Later sell 12 and accept 5 units into the same category. Import at 14:00. Discrepancy is -20; current corrected stock is 73, not 80.

**Late pre-count sale:** a five-unit sale actually happened before 10:00 and was already reflected in the physical 80, but reaches the server after reconciliation. Book quantity at cutoff becomes 95; discrepancy becomes -15. Preserve the sale and original observation, append an audited reconciliation revision/compensation, and keep current stock at 73 under the same later movements. Do not produce 68 by charging it twice.

**Late post-count sale:** an additional five-unit sale physically happened after the count but arrives later. It reduces current stock once, from 73 to 68 under otherwise unchanged inputs.

**Newer count exists:** Monday observation 80, Tuesday observation 60, five later units sold. Import Monday on Wednesday. Present stock remains 55; historical interval discrepancies can change, but the newer physical observation remains the later reference point.

**Repeated completion:** accept a count at 10, sell two, replay the original submission/completion. Current stock remains eight; repeat the original receipt without applying a new count adjustment.

### Missing history and revised projections

Persist valid physical observations without pretending all offline movements are already known. Expose waiting-for-history, needs-review, reconciled-through-revision, and superseded/corrected states distinctly. A syntactically valid file is not proof of complete stock reconciliation. Track coverage for the known sources; define late-event handling even after a provisional coverage assessment.

Original observations and application receipts remain immutable. A later movement or authorized correction may produce a new derived reconciliation revision. Preserve why a prior discrepancy changed. Do not mutate a settled physical observation through a generic edit/reopen action.

Late/backdated inventory evidence does not silently rewrite paid-sale amounts, customer receipts, shift-close submissions, or closed-period financial records. Backdate authorization, limits of retained history, material conflict authority and financial-period treatment remain explicit policy dependencies. This clarification does not choose a new arbitrary backdate limit.

## 7. Preview, validation, identity and commit behavior

### Validation and preview

Staging performs no stock writes. Before submission, show the actual count cutoff, physical quantity, historical reconstructed book quantity, discrepancy, intervening movements, projected balance as of the preview revision, and evidence gaps per row. The export-time book balance cannot substitute for reconstructed stock at the observation time.

A completely untouched prefilled row is uncounted, not an error and not zero. A row with some entered observation data but a missing required quantity/time is incomplete and must be shown as such, never silently omitted. The user can correct it or explicitly retain/exclude it as unfinished before submitting a clearly displayed subset. Never apply the valid-looking portion of a malformed file silently.

Validate wrong-location uploads, unsupported template revisions, corrupted/unknown IDs, duplicate observations, unsupported units/precision, missing evidence, impossible/future times, schema violations, unsafe workbook structures, and applicable permissions/period restrictions. Archived or renamed items require authoritative historical resolution; do not discard genuine historical evidence simply because the current catalog differs. Unresolvable cases go to review rather than guessed mappings.

### Proposed unit of application

Persist the explicitly selected, validated submission observations and their immutable command receipt atomically in a short database transaction. A hard validation error prevents that selected submission from being accepted. After acceptance, reconciliation status can differ by row because evidence/conflicts differ; the session must visibly summarize those states. Do not display a blanket "all stock corrected" message while some accepted rows await history or review.

Every reconciliation command must itself atomically commit its reconciliation revision/receipt, inventory adjustments or canonical projection updates, and audit evidence. An observation receipt means the observation was durably accepted; it must not claim stock was applied until the corresponding reconciliation commits. A retry of either command must not duplicate its effects.

Coordinate reconciliation with all stock writers using the shared stock-scope locking/revision strategy. Do not hold locks while staff count, edit the spreadsheet, inspect a preview, or wait for synchronization.

Sales continuing after preview are expected. Revalidate scope, inputs and coverage at commit and recompute derived effects against the current revision. Do not apply a stale forecasted stock value. Ordinary intervening movements must not cause an endless stale-preview loop; if newly discovered evidence materially changes the proposed discrepancy or conflict status, show the revision and request the necessary clarification/confirmation.

### Duplicate submission and correction

The same logical submission under the same command identity returns the original result without additional effects. Fingerprint the canonical normalized immutable fields/rows, not workbook ZIP bytes or filename. Sorting rows, changing formatting or renaming the file is not a new count. Keep the raw file hash separately as provenance.

Before acceptance, a draft can be explicitly edited and versioned. After acceptance, a changed quantity, cutoff or identity under the old submission key is a conflict, not a retry. A correction is a new linked command/observation with its own authorization and audit. A genuinely new physical recount gets a new session/observation identity. Regenerating an existing template must not quietly create a new count identity.
